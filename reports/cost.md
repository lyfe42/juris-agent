# F31 成本报表

> **一句话**：这份报表回答「一次问答要花多少钱、钱花在哪一步、少注入几条法条值不值」。

> ⚠️ **先说清楚三件事，否则这张表的数会被误用：**
> ① **这是估算，不是账单。** 算的是「把这段 prompt 发过去要花多少」；
>    不含重试、不含失败但已计费的调用、不含供应商侧的口径差异。
> ② **每个数字都绑着一天的牌价**（见「测量条件」里的 `as_of`）。
>    没有日期的价格数字，三个月后就是一段没法验证的历史。
> ③ **这里的模型是推理模型，思考过程按输出计费**——所以「答案短」
>    不等于「便宜」。表里专门有一列「其中思考」，
>    它就是「看着没说什么，钱却花掉了」的那部分。

## 测量条件

- 生成模型：`deepseek-flash`；牌价表 `pricing.yaml`，**as_of = 2026-10**（输入 2.0/百万、输出 8.0/百万，CNY）
- 主报表：**8/8 题成功**，`inject_k = 8`（生产默认）
- 题目是 **8 条混合题**（法条问答 / 计算题 / 超纲拒答 / 闲聊）——只用一种题型会得出错误的「平均成本」
- 缓存折算系数 `hit_discount = 0.1`（**只影响钱那一列，不影响任何指标**）
- 模式：**真调 API**。理由见 `scripts/cost_report.py` 开头——
  重放模式下客户端刻意不记 token，分项数字会全是 0。

## 一、钱花在哪：按阶段拆

| 阶段 | 干什么的 | 调用 | 输入 token | 输出 token | 其中思考 | 缓存命中输入 | 金额 | 占成本 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 工具循环 | 模型挑工具、填参数（只有计算题会走） | 8 | 45,653 | 3,519 | 1,065 | 36,224 | ¥0.054255 | 34.1% |
| 生成答案 | 拿着检索到的法条写答案（**产出的主体在这里**） | 6 | 15,173 | 10,861 | 5,957 | 7,296 | ¥0.104101 | 65.5% |
| 闲聊 | 寒暄（固定文案也能兜，有模型就用模型回） | 1 | 118 | 43 | 0 | 0 | ¥0.000580 | 0.4% |
| **合计** | | **15** | **60,944** | **14,423** | **7,022** | **43,520** | **¥0.158936** | 100% |

怎么读这张表：

- **阶段是按调用特征反推的**，不是模型自己报的——`LLMClient` 只收到
  messages，它不知道这次调用是「挑工具」还是「写答案」。
  判定规则写在 `cost_report.py` 的 `classify()` 里，很短，值得看一眼。
- **「其他/未分类」必须是 0 行。** 它不是「其他开销」，而是
  **「分类规则破了」的报警灯**——真出现非零，说明有人改了那几个 system 提示，
  而报表不会报错，只会安静地把钱记到这一行。
- **「其中思考」是输出的一部分**（供应商就是这么计的），不额外加钱。
  单独列出来是为了回答「答案很短为什么还这么贵」。
- **`生成答案` 那一行是省钱的靶心。** 它的输入 token 由两部分拼成：
  固定的提示词 + 检索出来注入的法条。后者是唯一能大改的旋钮，见第四章。

## 二、prompt 缓存到底省了没有

| 指标 | 值 |
|---|---:|
| 输入 token 合计 | 60,944 |
| 其中命中缓存 | 43,520 |
| 其中未命中 | 17,424 |
| **缓存命中率** | **71.4%** |
| 输入这一项的钱：命中部分不打折 | ¥0.121888 |
| 输入这一项的钱：实际（命中部分打 0.1 折） | ¥0.043552 |
| **缓存省掉的输入开销** | **64.3%** |
| 没拿到 usage 的调用 | 0 次 |

命中都发生在哪一步（也对应第一章那张表的「缓存命中输入」列）：

- **工具循环**：36,224 token
- **生成答案**：7,296 token

> ### 这里要修正一个很常见的直觉
>
> 本节初稿写的是「命中率应该很低，缓存省不了钱」。
> **实测把它推翻了**：命中率 71.4%，输入开销省掉 64.3%。
> 「开了 prompt 缓存能省一大截」这句话**方向是对的**——
> 但**理由几乎总是说错的**，而理由决定了它**能不能扩**。
>
> 缓存只对「**前缀一模一样**」的请求有效。本项目真正命中的是两种前缀：
>
> ① **同一题的工具循环里，后一次调用把前一次的整段对话又发了一遍**——
>    工具定义、系统提示、前面几轮的问答，全都是上一次请求的**前缀**。
>    命中的大头在这里（看上面那份分步清单）。
> ② **不同题之间**，工具定义 + 系统提示这一段前缀是相同的，
>    所以从第二题起，第一段就命中。
>
> **这两种都不是「用户越多越省」。** 更准确的说法是
> **「同一段前缀被反复发」**。这带来三个不能忽略的后果：
>
> - **一轮里的第一次调用必定是冷的**（没有任何前缀可命中），
>   省下来的是后面几次。所以**单题成本里那笔「冷启动」是躲不掉的**。
> - **命中率会被「轮数」影响，而不是被「用户数」影响。**
>   工具循环绕的圈越多，重复发的前缀越多，命中率越高——
>   换句话说**这一列会因为模型爱多绕两圈而变好看**，
>   别把它当成「我们优化得好」的证据。要看省钱，看钱那一列。
> - **缓存有存活时间，这里没测。** 两次问答隔久了缓存就过期，
>   命中率会掉。本表是**连续跑**出来的，所以它是一个**偏乐观的上界**。

## 三、一次问答多少钱

| 题 | 路由 | 调用次数 | 输入 token | 输出 token | 其中思考 | 金额 | 耗时 |
|---|---|---:|---:|---:|---:|---:|---:|
| 试用期最长可以约定多久 | calc | 3 | 13,658 | 1,588 | 503 | ¥0.021127 | 16.9s |
| 经济补偿怎么算 | calc | 3 | 15,895 | 3,674 | 1,755 | ¥0.040446 | 25.5s |
| 被违法辞退能拿多少赔偿 | calc | 3 | 15,072 | 3,069 | 1,495 | ¥0.036725 | 22.5s |
| 竞业限制没约定补偿怎么办 | law | 1 | 890 | 2,155 | 1,226 | ¥0.017868 | 15.2s |
| 劳动合同到期不续签有补偿吗 | law | 1 | 1,011 | 1,826 | 1,221 | ¥0.016400 | 13.1s |
| 加班费怎么算 | calc | 3 | 14,300 | 2,068 | 822 | ¥0.025790 | 15.3s |
| 帮我写一首关于秋天的诗 | out_of_scope | 0 | 0 | 0 | 0 | ¥0.000000 | 0.0s |
| 你好 | chitchat | 1 | 118 | 43 | 0 | ¥0.000580 | 1.0s |

- **中位数（P50）：¥0.021127**
- **P95：¥0.040446**
- **最贵 / 最便宜：¥0.040446（经济补偿怎么算） / ¥0.000580（你好），差了 69.7 倍**——**注意这个倍数是拿最贵那条跟最便宜那条比，不是「平均值上下浮动」**
- **另有 1 条题是 ¥0**（帮我写一首关于秋天的诗）——**它们不参与上面那个倍数**：0 元不是一个「价格」，是「这笔交易没发生」。硬拿它做分母会得到一个假的「无穷倍」
- 合计：¥0.158936（8 题，15 次模型调用）

怎么读这张表：

- **题与题之间差好几倍，别拿一个「平均价」去拍预算。**
  闲聊题一次调用就完，计算题要跑工具循环（多轮调用，每轮输出都被思考撑满）。
  预算要按**最贵那一档**拍，不是按中位数拍。
- **P95 在这点样本下基本没有统计意义**，它的用途是给出量级，
  不是拿来当 SLO。样本量写在「测量条件」里，别忽略。
- **1 条超纲题是 0 次调用**——它们在规则层就被挡掉了，一次模型都没调。这就是「拒答」该有的成本：**0**。（省的不只是提示词那点钱，是**一整次问答**。）

## 四、成本 vs 召回：少注入几条值不值

| `inject_k` | 生成阶段平均输入 token | 每题平均成本 | hit@k（gold 在里面吗） | art@k（gold 覆盖了多少） | 召回样本 |
|---:|---:|---:|---:|---:|---:|
| 2 | 2661 | ¥0.029159 | 0.866 | 0.819 | 269 题 |
| 4 | 3018 | ¥0.030933 | 0.929 | 0.878 | 269 题 |
| 8 | 3322 | ¥0.032303 | 0.967 | 0.920 | 269 题 |
| 12 | 3486 | ¥0.033331 | 0.981 | 0.934 | 269 题 |

怎么读这条曲线：

- **横轴是「注入几条法条」**，也就是发出去的 prompt 里塞多少上下文。
  这是本项目里**最直接的省钱旋钮**——它同时决定 token 和召回，
  所以「省了多少」和「掉了多少」必须在同一张表里看。
- **两半的样本量不一样，表里分开标了。**
  召回那半边**不调模型、免费**，跑的是全量 gold（本次 269 题）；
  成本那半边要真调模型，只跑了 3 题。
  **两边不同源**，所以下面的对比只能当量级判断，不是会计。
- **`art@k` 比 `hit@k` 更能说明问题。** 组合题（一问要引好几条）
  少注入时 `hit` 可能还撑着（碰到一条就算命中），
  而 `art` 会开始掉——那才是「答不全」的信号。
- **本次实测的取舍（这就是这条曲线的结论）：**
- 注入条数从 `8` 降到 `2`：生成阶段的输入 token 3322 → 2661（降 19.9%），
  **每题成本 ¥0.032303 → ¥0.029159，只降 9.7%**。
- 但 `hit@k` 从 0.967 掉到 0.866（**掉 10.0 个百分点**），`art@k` 从 0.920 掉到 0.819。
- → 代价大于收益：省下的钱比掉掉的召回还少，**这一档不划算**。
- **为什么省钱这么有限？看第一章：`工具循环` 那一档占了全场成本的 34.1%，而它完全不随 `inject_k` 变**（工具循环里塞的是工具定义和前几轮的对话，不是检索结果）。
  **所以「靠少注入法条来省钱」在这个系统里天花板很低。**
  真正有空间的省钱方向在别处：少绕一轮工具循环、把工具定义压短——
  **那两件事改的是占大头的那一档，不是这一条曲线。**
- ⚠️ **这条曲线能定方向，不能定小数点。**
  真正的用法是「选一个点，并说清代价」：
  「注入 N 条，成本降到 X%，召回掉 Y 个点」。
  只说「我们做了成本优化」等于什么都没说。
- ⚠️ **hit@k 的分母是全部 gold，而成本只测了几题。**
  想拿这条曲线去定案，先把成本那半边扩到同一批题上（`--sweep-n`）——
  **那要花钱，但只有那样两个数才是同一个总体的。**

## 五、这份报表**测不到**什么

1. **不含重试与失败调用。** 只能统计「我们拿得到 usage」的调用。
   本次有 0 次调用没拿到 usage。
   供应商扣了钱而我们没拿到数的那种，这张表看不见。
2. **不是账单。** 真实花销要看供应商控制台。
3. **一次运行的量，不是「长期平均」。** 题换了、注入条数变了，数就变。
4. **缓存那一章偏乐观。** 同一次运行内部，前缀比线上更容易重复；
   而且这里没测缓存过期。所以命中率是**上界**，不是线上实测值。
