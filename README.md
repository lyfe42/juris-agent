# juris-agent

**可溯源劳动法咨询 Agent —— 从 RAG 到 Agent 的可靠性工程与评测体系**

面向求职者与在职员工的劳动法自助咨询：签合同前查试用期与竞业限制、算加班费与经济补偿、
判断解除是否合法。答案一律附法条编号与原文，超出范围时明确拒答而不是硬编。

> **定位说明（为什么领域只是载体）**
>
> 法律语料被选为载体，是因为它是**唯一能让检索指标程序化计算**的领域——法条有编号，
> 可以直接当 gold，Recall@k 与引用准确率不需要 LLM 打分就能算出来。换成客服或公司文档，
> 评测层的硬度会全部塌掉。
>
> 项目真正的厚度在**可靠性工程与评测体系**：消融矩阵（把零件逐个关掉，看指标掉多少）、
> 故障注入（故意制造故障，看系统在坏情况下会怎样）、失败归因收敛曲线（把错题分堆修，
> 看错误数一路降下来）。
> 这三块在同类项目里几乎没有（GitHub 上 `agent reliability fault injection` 只有 36 个
> 仓库、最高 3 star），但恰好是面试里追问最密集的地方。

## 三分钟用起来

**这一节是给「用它的人」看的**；下面各节是给「改它的人」看的。
分成两拨是因为这两件事的读者关心的问题完全不同——前者只想知道"怎么问一句话"，
后者才关心"检索是怎么融合的"。

> 📖 **只想用它、不想读源码** → 直接看 [`USAGE.md`](USAGE.md)。
> 那份是完整的用户手册：四个入口分别什么时候用、网页上两块怎么区分、
> 算式的每一步怎么核对、工具箱里五个计算器各容易填错什么、装不上怎么办。
> 下面这一节是它的精简版。

### 1. 装

```bash
uv sync --extra ml             # 核心 + 检索栈（CUDA torch，约 2.5GB）
cp .env.example .env           # 然后把 DEEPSEEK_API_KEY 填进去
```

> 明细和"为什么卡在 Python 3.12"见下面的[安装](#安装)。

### 2. 先体检

```bash
juris doctor
```

缺什么就说缺什么，**退出码 0 = 能答问题、1 = 不能**，所以也能塞进脚本。
装不起来时它会**按最常见的顺序**列排查步骤（`.env` 有没有、key 填没填、
`--extra ml` 装没装、语料建没建、huggingface 要不要换镜像）。

### 3. 问一个

```bash
juris ask "公司裁员，我干了 3 年月薪 1 万，能赔多少？"
```

```bash
juris ask "试用期最长能有多久？" --stream --trace
```

`--stream` 是打字机效果（边生成边打），`--trace` 会再打一份**执行轨迹**——
走了哪几个节点、各花多久、token 花在哪。加 `--json` 输出一整段 JSON
（给脚本用，**stdout 里只有 JSON**，日志全在 stderr）。

### 4. 连着聊

```bash
juris chat
```

多轮是记忆层在起作用，**同一段会话里它会记住你报过的月薪、工龄、地点**，
所以第一句说完背景，第二句直接问结论就够了：

```
> 我在西安，月薪 12000，干了 2 年，被裁了
  …（答：能拿 24000）
> 那到底能赔多少？
  …（答：24000 元 = 12000 × 2 年，并检查了当地社平三倍封顶）
```

> `/new` 开一段新会话，`/session` 看当前会话 id，`--session <id>` 能接着上次聊。

### 5. 起网页

```bash
juris serve                    # http://127.0.0.1:8000
```

页面左上角有两个视图：**问答**（走模型，要 key）和**工具箱**
（直接调五个计算器，**不要 key、不花钱、毫秒级**）。
只想算个数的话别去聊天框里等——工具箱那边同一组输入永远同一个答案。

### 6. 或者直接写 Python

```python
from juris_agent import ask

a = ask("被辞退有补偿吗？")
print(a.text)        # 答案 + 引用法条（带原文）
print(a.cost_text)   # 这一轮真花了多少
print(a.citations)   # [《劳动合同法》第四十七条, …]，每条都能回到原文
```

多轮用同一个 `session_id`；要长期持有就 `with JurisAgent() as agent:`。
**门面的完整契约（懒加载、装不起来时抛什么、`close()` 之后还能不能用）
写在 [`src/juris_agent/client.py`](src/juris_agent/client.py) 的 docstring 里。**

> ⚠️ 在这之前，"用一下这个 Agent"要自己攒五样东西
> （settings、retriever、llm、registry、executor）才够 `make_runner` 开跑，
> 而且里面藏着**三个只有读过源码才知道的约束**（重装配要进程级共享、
> 没有 key 会在第三个 import 里抛、成本记账必须在同一个线程里开账）。
> 门面就是把这三个约束收起来——**它不改变任何行为**，只是不再要求调用方知道这些。

### 装不起来怎么办

`juris doctor` 已经会告诉你缺什么。如果它报的东西看不懂，按这个顺序试：

| 症状 | 先看这个 |
|---|---|
| `检索器未装配：ModuleNotFoundError` | `uv sync --extra ml`（检索栈在可选的 `ml` 组里） |
| `检索器未装配：… 语料/索引不存在` | `uv run python scripts/build_index.py` |
| 卡在下载模型 / `ConnectionError` | `.env` 里设 `HF_ENDPOINT=https://hf-mirror.com` |
| `LLM 未装配：没有 DEEPSEEK_API_KEY` | 复制 `.env.example` 为 `.env` 并填 key |
| 想在**不花钱、不装模型**时试一遍 | `juris doctor` 不需要 key；`uv run python scripts/demo.py` 支持回放模式 |

⚠️ 修完配置后**要重新起一个进程**（`juris` 每次都是新进程，天生就是重装的）。
如果在同一个 Python 进程里改（REPL、notebook），得新建一个 `JurisAgent`
或调 `agent.close()`——**装失败的那个结果会被记住**，
不然每问一题都要先卡几十秒再报同一个错（理由见 `client.py` 的 `_ensure`）。

## 安装

工具层只需要 pydantic，**不需要** GPU 栈：

```bash
uv sync --extra dev            # 工具层 + 测试，秒级
pytest                         # 全部通过
```

检索层需要 CUDA torch 与 embedding/rerank 模型（约 2.5GB）：

```bash
uv sync --extra ml --extra dev # 本机 RTX 4060，走 cu124 源（见 pyproject.toml）
```

`uv sync` 会顺手装上 `juris` 这个命令（`[project.scripts]` → `src/juris_agent/cli.py:main`）。
装完可以先跑 `juris doctor` 看环境齐不齐，用法见上面的[三分钟用起来](#三分钟用起来)。

> ⚠️ **入口必须写成 `juris_agent.cli:main`，不能写成 `main()`。**
> `console_scripts` 生成的包装器是 `sys.exit(main())`——写 `main()` 就变成
> 把返回值当函数再调一次，报 `TypeError: 'int' object is not callable`，
> 而且栈里一行自己的代码都没有。同理 `main()` 里也不能自己 `sys.exit()`，
> 那样单测没法直接调它（`SystemExit` 会从断言中间穿出去）。

> `HF_ENDPOINT` 必须在 `transformers` 首次 import **之前**生效。`src/juris_agent/__init__.py`
> 里的引导负责这件事——任何 `from juris_agent.x import y` 都会先执行它。详见该文件 docstring。
> 也正因为这个，`juris_agent` 对外的门面（`ask` / `JurisAgent`）走的是
> **PEP 562 的模块级 `__getattr__`** 懒导出，而不是顶部一句 `from .client import ask`——
> 后者会把 pydantic-settings 拉进引导阶段。
> 代价是 IDE 补全可能看不到这几个名字（`__all__` 是给它的提示）。

复制 `.env.example` 为 `.env` 并填入 `DEEPSEEK_API_KEY`。`.env` 已在 `.gitignore` 中。

## 工具层设计要点

一次 `ToolExecutor.call()` 的流水线。**人话版**：先查这个请求是不是刚发过（是就直接返回上次
结果）→ 校验参数对不对（不对就退回给模型改）→ 问熔断器放不放行（某个下游连续挂了就先别调
它）→ 真正调用 → 失败就隔一段时间重试、间隔越拉越长 → 还不成就走备用实现（降级）。

```
幂等键命中? ──是──> 直接返回缓存（不消耗重试预算）
     │否
入参 schema 校验 ──失败──> 返回字段级错误，不重试（同样入参必然同样失败）
     │通过
熔断器放行? ──否──> 返回 CircuitOpenError（不发起调用，保护下游）
     │是
┌─> 调用（带超时）
│     失败且可重试且还有预算 ──> 指数退避(±20% 抖动) ──┐
└─────────────────────────────────────────────────────┘
     │成功                      │重试耗尽
出参 schema 校验                降级实现（若有）──> degraded
     │                          │无降级
   ok                         failed（附结构化建议）
```

几个刻意的决定：

- **失败的返回值是结构化的**（`error_type` / `retry_policy` / `hint`），不是空字符串。
  模型拿到结构化反馈才有机会换工具或改参数；拿到空串只能原地重试。
- **4xx 不重试**。参数错误、鉴权失败、额度耗尽，重试只会浪费时间和额度——
  故障注入实验里表现为"重试 3 次仍失败，却把下游负载放大了 3 倍"（见下）。
- **被熔断拒绝的调用不计入熔断窗口**，否则拒绝次数自我强化，熔断永不解开。
- **入参校验失败不计入熔断**：那是模型的错，不是工具的错。
- **熔断窗口单位是"一次逻辑调用"**（重试 3 次后成功算 1 次成功），
  `attempts` 字段单独记录物理尝试次数供报表用。
- **时钟、随机数、sleep 全部可注入**，所以整套执行层测试跑在毫秒级且完全可复现。

## 实验一：工具层故障注入（已有结果）

`scripts/fault_inject.py` 用**三臂对照 + 配对种子**（各臂共用同一份调用计划与同一随机种子，
故障序列因此逐条对应）分离出每个机制各自的贡献。两臂只能回答"有没有用"，三臂才能回答
**"收益来自哪个机制"**。

```bash
python scripts/fault_inject.py --error-rate 0.3 --calls 300
```

**场景 A — 均匀随机故障（每工具独立 30% 失败，300 次调用）**

| 臂 | 成功率 | 下游调用量 | 熔断跳闸 |
|---|---:|---:|---:|
| 裸调用（无重试 / 无熔断） | 67.7% | 300 | 0 |
| 仅重试退避（无熔断） | 87.0% | 386 | 0 |
| 重试退避 + 熔断 | 87.0% | 386 | 0 |

**场景 B — 单工具持续故障（一个下游 100% 不可用）**

| 臂 | 成功率 | 下游调用量 | 均耗时(模拟) | 熔断跳闸 |
|---|---:|---:|---:|---:|
| 裸调用 | 0.0% | 300 | 120ms | 0 |
| 仅重试退避 | 0.0% | 900 | 360ms | 0 |
| 重试退避 + 熔断 | 0.0% | **15** | **6ms** | 1 |

三条结论，都是被这两个场景逼出来的：

1. **重试的收益只在"故障是零星分散的"时候存在**（场景 A：+19.3 个百分点）。
2. **熔断在场景 A 一次都没跳闸**——单工具 30% 的失败率够不到 50% 阈值。
   这不是配置错误，而是说明**低幅度的错误扩散本来就不该触发熔断**。
   只跑场景 A 会得出"熔断没用"的错误结论。
3. **熔断不提高成功率**（场景 B 三臂都是 0.0%），它做的是另外两件事：
   把下游负载从 900 压到 15 次（**60 倍**），把用户的失败等待从 360ms 压到 6ms。
   **重试单独用是有害的**——它让一个已经过载的下游承受 3 倍流量。

> ⚠️ 这里所有延迟都是**模拟量**（每次物理尝试计价 120ms），不是实测 P95。
> 实测 QPS/延迟由 `scripts/bench_qps.py` 单独产出，见
> [`reports/qps.md`](reports/qps.md)（三档分开报：mock / nollm / real）。
> 完整报告见 [`reports/fault_injection.md`](reports/fault_injection.md)，
> 结构化原始数字见 `reports/fault_injection.json`（可作回归基线）。

## 实验二：检索消融矩阵（269 题，全链路）

### 结论一：融合**打不过**最强的单路——而且三次测量都指向同一处

稠密单独 **0.907**，BM25 单独 **0.606**，两者等权 RRF **0.866**。
**加一路更弱的检索器，把更强的那个拖下去了 4.1 个点。**

权重扫描把机制坐实了——注意 `hit@5` 和 `MRR@10` 说的是**两件不同的事**：

| BM25 权重 | hit@5 | MRR@10 |
|---:|---:|---:|
| 0（= 稠密单独，自检行） | 0.907 | **0.768** |
| 0.25 | 0.903 | 0.730 |
| 0.50 | 0.903 | 0.717 |
| 0.75 | 0.903 | 0.713 |
| 1.00（等权） | 0.866 | **0.689** |

- `hit@5` 在 0.25～0.75 之间**持平在 0.903**，看起来"加一点 BM25 无害"；
- 但 `MRR@10` **随权重单调下降**：0.768 → 0.730 → 0.717 → 0.713 → 0.689。

**只看 hit@5 会得出"BM25 加点没关系"，看 MRR 才知道它一直在把正确答案往下挤。**
这就是为什么两个指标都不能省。

> 这个结论在 21 题的人工集上是 0.857 vs 0.714（差 14 个点），在 269 题上是
> 0.907 vs 0.866（差 4 个点）。**方向一致、幅度差三倍**——小样本会把差距夸大，
> 这也是我把机器集造出来的原因之一。

**机制是什么？`scripts/diagnose.py` 逐题摊开之后就一句话：RRF 给 BM25 的第 1 名
和稠密的第 1 名**同样的分**（`1/(k+1)`），不管 BM25 那个"第 1 名"有多烂。**

两个真实例子（均出自人工题，[`reports/diagnosis.md`](reports/diagnosis.md) 有全文）：

| 题 | 稠密单独 | BM25 单独 | RRF 融合后 |
|---|---|---|---|
| `g007` 公司每月最多能安排我加班多少小时？（gold = 劳动法第41条） | **第 1 名** | 第 8 名（全是民法典噪声） | 掉到第 2 |
| `g015` 劳务派遣工能和正式员工拿一样工资吗？（gold = 劳动合同法第63条） | **第 1 名** | 第 17 名 | **掉到第 7** |

`g007` 里 BM25 的第 1 名是劳动合同法第31条（讲"加班需协商"，不是时长上限），
它拿到 `1/61`；稠密那个正确的第 1 名也拿 `1/61`——同分，然后按 id 字典序，
`lcl#31` 排在 `ldf#41` 前面。**正确答案因为一个无关命中拿了同分而退位。**

**最锋利的一条证据在"独赢题"统计里：**

| 臂 | 命中 | 平均首位名次 | **独赢题数** |
|---|---:|---:|---:|
| `B/dense-only` | 263/269 | **2.06** | **3** |
| `B/bm25-only` | 205/269 | 3.51 | **0** |
| `B/bm25+dense RRF` | 260/269 | 2.42 | 0 |
| `B/bm25+dense 加权求和` | 260/269 | 2.23 | 0 |

**BM25 在这份语料上的独赢题是 0 道。** 269 道题里，没有一道是"稠密找不到、
只有 BM25 能找到"的——而稠密有 3 道独赢题，RRF 把这 3 道**全部丢掉**。
这比"融合低了 4 个点"更直接地回答了"为什么还要 BM25"这个问题：
**在这份语料上，BM25 的信息已经被稠密覆盖，多出来的部分全是噪声。**

### 结论二：近似检索在这个规模上**纯亏**

`F/dense 精确` 0.907 → `F/dense IVF(nprobe=1)` **0.714**，掉 19.3 个点，
而 **p50 一点没变（都是 7ms）**。

这就是"这个规模不该上向量库"的实测依据：1730 条的暴力点积已经是微秒级，
IVF 省不出时间，只丢 Recall。详见 [`docs/tech-choices.md`](docs/tech-choices.md) §4。

### 结论三：两个大收益部件，代价差 30 倍

| 加装 | hit@5 变化 | MRR@10 变化 | p50 耗时变化 | 性价比 |
|---|---:|---:|---|---|
| 精排（cross-encoder） | +0.078 | +0.130 | 12 → **230ms**（19×） | 高 |
| LLM 改写 | +0.086 | +0.126 | 12 → **6684~6792ms**（约 570×） | **低** |
| 同义词表 | +0.008 | +0.011 | 12 → 23ms（2×） | 待定，见下 |

精排和 LLM 改写的**收益在同一个量级**（hit@5 上 +0.078 vs +0.086，MRR 上
+0.130 vs +0.126，互有高低），但 LLM 改写要
**多花约 570 倍的时间**（每题 6.7~6.8 秒——它是推理模型，思维链也要算 token）。
在真实产品里这个延迟是不能接受的，所以**正确的组合是精排 + 同义词表**，
LLM 改写只在离线批处理（比如给整库预生成同义变体）时才划算。

> 这条对比只有在**同时报指标和延迟**时才看得出来。只报 hit@5 的话，
> LLM 改写看起来就是"最好的那个"，而它是没法上线的那个。

#### ⚠️ 关于 LLM 改写那一行，有三件事必须先说清楚

这三件都是**实测撞出来的**，不是设计时想到的。它们合起来说明一件事：
**凡是走 LLM 的那一行，它的数字比别的行"软"。**

**（1）`temperature=0` 不等于可复现——我被自己的实测打了脸。**

常识是"`temperature=0` 就是确定性的"，我照着这个常识把验收标准从
"跑 3 次报均值±std"改成了"`temperature=0` + 缓存，让噪声根本不存在"。
**实测把这个想法推翻了**：同一道题连着问两次，**20/20 都给了不同的改写**。

变体语义上很接近（都是"试用期 期限 上限 六个月"这类关键词组合），
但**措辞不同**——而 BM25 匹配的是字面，所以检索结果真的会变。
三次独立采样下这一臂的 hit@5 是 **0.937 / 0.948 / 0.952**。

**缓存只买了"稳定"，没买"无偏"**：`replay` 模式下两次运行逐位一致
（缓存返回同一份输出），但**建立缓存的那一次采样本身不可复现**。
**原验收标准（跑 N 次报均值±std）是对的，我改错了。**

**（2）延迟塌了 160 倍，而指标一模一样——缓存会摧毁延迟测量。**

| 同一条臂 `D/+LLM 改写` | p50 | p95 | 说明 |
|---|---:|---:|---|
| 缓存未命中（`off` 模式） | **6684~6792 ms** | **12101 ms** | 真实推理耗时（三次采样） |
| 全部命中缓存（`record`） | **42 ms** | — | 这是"读一个 JSON 文件"的耗时 |

**指标在两种模式下完全相同。** 也就是说，如果只跑 `record` 模式，
你会看到一个"每题 42 毫秒"的 LLM 改写臂，并据此得出错误结论。
`scripts/ablation.py` 现在读 LLM 模式，对走 LLM 的臂在表里打 ⚠️ 标记。

> 分段的数字更直观：`off` 模式下一次调用 p50 = 6684ms，其中
> **`rewrite` 段独占 6556ms（98%）**，检索本身只占不到 130ms。
> p95 更是到 **12.1 秒**——这个尾延迟在对话产品里等于用户已经走开了。

**（3）一个静默失败：约 8%~12% 的改写调用失败，而报告里看不出来。**

改写失败时**不抛错**，退化成"这一题不改写"（这是对的设计——单题失败不该
让整条评测链断掉）。但它当时**只记了计数器，没进报表**。跑满 269 题（含一次预热）
共 **270 次调用，三次重跑分别失败 21 / 22 / 32 次（7.8% ~ 11.8%）**，
原因几乎全是 `LLMError`（少量 `LLMTruncated`）。**这个数字在在线重跑时会变**，
因为失败调用不入缓存（存了等于把一次网络抖动永久钉进 fixture）——
但 `replay` 会把它重新钉死（实测复现出同样的 21/270，那些题变成
「缓存未命中 ⇒ 必然失败」）。**变的是在线重跑，不变的是 replay。**

**也就是说这一臂的数字里混着约 8%~12% 根本没改写的题，而看表的人无从知道。**
这跟项目自己在工具层批评的"静默降级"是同一类错误——只不过这次发生在评测代码自己身上。
已修：`failure_reasons` 分桶记录原因，`ablation.py` 会把它打进报告
（见 [`reports/ablation.md`](reports/ablation.md) 里 `D/+LLM 改写` 那一行下面的注）。

### 结论四：同义词表的收益**在 test 上是负的**（如实记录）

`D/+同义词表` 总体 +0.008，看着是正收益。但拆开 dev/test：

- dev：0.852 → **0.875**（+0.023）
- test：0.892 → **0.871**（**−0.021**）

**方向相反，且都在噪声量级。** 同义词表是在 dev 上逐条加词加出来的，
所以 dev 涨、test 不涨，是典型的**过拟合到 dev**。诚实结论是
**这一臂目前没有可证实的收益**，而不是"+0.8 个点有用"。

### 结论五：邻条扩展在**指标上是零效应**，而且这是设计使然

`C/+邻条扩展±1` 与 `C/融合（基线）` 的**每一项指标逐位相同**，
`C/+精排+邻条` 与 `C/+精排` 也逐位相同。

这不是 bug，是必然：扩展出来的条**一律追加在结果尾部**（"顺带捞的"不许挤掉
"真正命中的"）。于是条级排名的**前 k 个位置完全不变**——逐题验证过，
269/269 题的前 10 个条级排名与基线一模一样。

**所以"邻条扩展有没有用"这个问题，本项目的指标口径回答不了。** 它声称的价值
（给生成模型更多上下文，补上"应当同时引用"的相邻条）在**生成层**，不在这张表上。
要么在生成层做对照实验，要么承认它现在只是一个没被证实的直觉。

### 结论六：切分臂的排序**被样本量翻转过**

21 题人工集上 `by_article`(0.571) > `by_article_plus_context`(0.524)；
269 题上反过来：`by_article_plus_context`(0.613) > `by_article`(0.606)。

**差 0.007——远小于噪声，真实结论是"这两个切分没有可区分的差别"。**
第一版 README 里那句"加章标题反而略降"是**小样本下过度解读**，已改。

站得住的只有一条：**定长切分明显最差**（0.394，比按条切低 21 个点，是唯一的
大差距）。定长窗口把条文从中间劈开，一块里半条法条配半条无关条文，
BM25 的分数被稀释。**切分策略值多少分，答案在这里。**

### 结论七：法律领域词典是中性（不是负收益）

词典 `on/off` 在全部 4 个切分臂上都是**打平或差 0.007 以内**（如 `by_article`
0.606 vs 0.599）。第一版收了 50 多个词时它是明显负收益（0.571 → 0.476），
机制已定位：**过度合并切断部分匹配**——查询"经济补偿金"被并成一整词，
而第四十七条写的是"经济补偿"，一词之差从第 8 名变成完全没命中。
收窄到只留 jieba 确实会切散的长词后，它回到中性。

**保留它是因为它不再是负收益，不是因为它有收益。** 这个区别在 README 里必须说清。

### 结论八：RRF 的 k 在这份数据上**几乎不重要**

k = 1 / 10 / 30 / 60 / 200 → hit@5 = 0.885 / 0.877 / 0.870 / 0.866 / 0.866。
k ≥ 60 之后完全不动；k=1 略好（+0.019）但 MRR 只差 0.027。

**"k 该选多少"的诚实答案是"在这份数据上感知不到，论文常写的 60 是个安全的默认"**——
而不是"我扫过参数曲线所以我知道 60 最优"。这条扫描真正排除的是
**k 小到极端时会变差**这个担心，以及"k 大到无穷会退化成按被召回次数排序"。

## Agent 层：一次提问在系统里怎么走

代码在 [`src/juris_agent/agent/graph.py`](src/juris_agent/agent/graph.py)，
用 LangGraph 搭成一个有向图。**人话版**：先翻出「这个用户之前说过什么」→
判断这题该查法条还是该算数 → 查/算 → 把结果和法条一起交给模型写答案 → 检查引用是不是真的存在 → 收尾。

```
START → remember ──> entry（路由：这题该走哪条路）
                       │
         ┌─────────────┼──────────────┐
         │             │              │
      法条问题     计算问题        超纲/闲聊
         │             │              │
      retrieve       tool ◄───┐        │
         │             │      │        │
         └──> guard ◄──┴──────┘        │
              （闸门）                  │
                │                       │
                └──────> generate <─────┘
                            │
                       guard（再过一次闸门）
                            │
                        finalize → END
```

**`remember` 为什么排在最前面、而且不进闸门？** 因为闸门（`guard`）唯一的工作是回答
「下一步去哪」，而 `remember` 的下一步**永远只有一个**——`entry`。没有分支要判断，
就没有闸门要过。**这不是省事，是因为一个只有一条出边的节点放进闸门里，
只会让闸门那段的代码多一个永远不会命中的分支。**

### 四道闸门：防止模型在工具循环里转圈出不来

模型调用工具这件事本身是个循环（模型说"我要调工具" → 系统执行 → 结果回给模型 →
模型可能又说"我要调工具"…）。**循环没有出口的代码等于死循环**，所以有四道闸门，
**全部集中在一个 `guard` 节点里**，而不是散落在各处：

| 闸门 | 人话 | 触发后 |
|---|---|---|
| 最大步数 | 「不管怎样，走了 N 步就必须收尾」 | 强制进生成 |
| 重复调用 | 「同一个工具、同一套参数，你已经调过了」 | 不执行，把上次结果原样还给它 |
| 无进展 | 「这一步和上一步拿到的东西一样，再走也没用」 | 强制进生成 |
| token 预算 | 「token 花超了」 | 强制进生成 |

**为什么全部塞在一个节点里**：四道闸门如果各写各的，就会出现「A 认为该走、
B 认为该停」这种自相矛盾的状态，而且改一个漏一个。合在一处，**每一步只有一次判决**。

**那它到底拦住过几次？** 实测见 [`reports/guard_ablation.md`](reports/guard_ablation.md)
（50 条诱导题 × 两臂）。三个结论都不是好听的：

1. **本项目只有 `calc` 那条路由上有工具循环**，走法条问答（`law`）是一步到底的
   （`nodes.py` 里 `retrieve` 出口写的是 `"tool" if route == "calc" else "generate"`，
   而 `generate` 只会去 `finalize`/`refuse`，**不会回到 `tool`**）。
   所以**在那条路上报「打转率 0%」是废话**——那条路根本没有圈可转。
   第一版 50 条对抗题里只有 10 条能走进循环，等于报了个假数字，重出题后是 34/50。
2. **有一类转法四道闸门全都拦不住**：每一步都真的有新产出的那种。拿它去测，
   四道全开和只留步数闸门**结果一模一样**（都是 100% 走光 12 步）。
   能靠"发现重复"防住的循环，②③ 防得很好（平均 13 步 → 6~8 步）；防不住的那种只剩硬上限。
   **「四道闸门 → 打转率归零」只对前三类形态成立。**
3. **真调模型跑这 50 条，死循环率是 0%，而且闸门一次都没触发。**
   「X% 降到 0%」这句话在这批数据上不成立，因为 **X 本身就是 0**。
   准确的说法是：**闸门的价值不是把 X 降下来，是把 X 的上限钉死**——
   它是一份有界的成本承诺，不是一项日常省钱措施。

### 引用校验：模型写的法条编号，系统要回头查一遍

模型生成完答案后，系统把它提到的 `lcl#47` 这种编号拿去和这一轮**真正检索到的**编号对，
对不上的标出来。**这一步存在的理由很直白**：模型编一个不存在的法条编号，
从文字上看和真的一模一样，只有比对才能发现。

## 实验三：长对话记忆消融（15 段 × 20 轮）

```bash
python scripts/memory_ablation.py     # 不需要 key、不需要 GPU
```

**先说清楚它测的是什么，这一条比主表重要：**

> **测的是「组装出来的提示词里，那个值还在不在」，不是「模型答得对不对」。**

三件事逼出这个口径：便宜（不需要调模型）、可复现（不受模型随机性影响）、
**失败可归因**——「值根本没进提示词」和「进去了但模型没用好」是两种完全不同的 bug，
混在一起测就分不出来。代价是它给出的是**上界**，不是端到端正确率。

**评测集**：15 段各 20 轮的多轮对话（`data/eval/memory_sessions.yaml`），
45 处探针、52 条期望值。探针故意埋在离说话那轮很远的地方（普遍隔 11~19 轮）。

| 策略 | **照抄型保持率** | 照抄型 通过/总数 | 换算型保持率 | 换算型 通过/总数 | 平均提示词 token |
|---|---|---|---|---|---|
| `no_memory`（只带最后一轮） | **0.000** | 0/32 | 0.000 | 0/20 | 49 |
| `sliding_window`（只看最近 6 轮） | **0.500** | 16/32 | 0.100 | 2/20 | 330 |
| `sliding_window_summary`（6 轮原文 + 摘要） | **0.188** | 6/32 | 0.150 | 3/20 | 265 |
| `layered`（四层） | **1.000** | 32/32 | 1.000 | 20/20 | 359 |

### 事实必须分两类，这条比主表重要

「记住」对两类事实是完全不同的难度：

| 类型 | 例子 | 用户原话里长什么样 | 谁能记住 |
|---|---|---|---|
| **照抄型** | 月工资 `12000`、城市 `西安`、离职日 `2024-05-10` | 原话里**就是**这个值 | 窗口 / 摘要 / 槽位都行 |
| **换算型** | 工作年限 `37`、是否提前通知 `False` | 「三年零一个月」「没提前通知」——**原文里根本没有这个值** | **只有槽位层** |

**为什么必须分开报**：换算型的事实原文里不存在那个写法，所以对它们来说
「四种策略对比」是个**假命题**——只有槽位层答得出来，剩下三个必然是 0。
**把两类混在一起，会得到一个好像是「插了槽位层就赢麻了」的表，其实那个差距是结构性的、是设计使然，不是测出来的。**

分类是**程序判的**（拿值的骨架去它原文那一轮里找），不是人在 YAML 里标的——
标错了没人看得出来，算出来的不会骗人。

### 曲线：隔得越久还记得吗

主表只有一个总数，它会把「最近的记得牢」和「远的全忘光」平均掉。要看形状得看这张：

| 策略 | 0-5 轮前 | 6-10 轮前 | 11+ 轮前 |
|---|---|---|---|
| `no_memory` | 0.00 | 0.00 | 0.00 |
| `sliding_window` | 1.00 | 1.00 | **0.00** |
| `sliding_window_summary` | 1.00 | 0.20 | 0.12 |
| `layered` | 1.00 | 1.00 | **1.00** |

两条策略花的 token 差不多（330 vs 359，**差 8%**），但**曲线的形状完全不一样**：

- `sliding_window` 是**硬边界**——窗口盖得住的记得住，盖不住的一律归零，**没有中间地带**。
  危险的地方就在这儿：**它在第 10 轮还是满分，第 11 轮直接变成 0 分，而用户完全不知道
  自己正跨过那条线。**
- `layered` 是平的，因为它把「必须记住的东西」从窗口里搬出来、放进一个**不吃压缩的槽位表**
  ——等于**花同样的钱，把那条硬边界抹掉了**。

### 摘要**输给**了纯滑动窗口（0.188 vs 0.500），这是反直觉的

两者**总预算一样**，区别在怎么花：`sliding_window` 把预算全砸在原文上（窗口被拉到 10 轮），
`sliding_window_summary` 保持 6 轮原文 + 拿剩下的预算放摘要。

而这里的摘要是**规则拼的**——从一段历史里挑几句用户原话串起来。
**挑中的句子就是全部；没被挑中的，连数字带上下文一起没了。**
结论一句话：**摘要能把「聊过什么」带过去，带不过去精确的值。这就是为什么槽位层必须单独存在——精确的事实绝不交给有损压缩承载。**

### ⚠️ `layered` 那 1.000 分，到底是谁挣的

这一节是**泼冷水**，别跳过。`layered` 拿满分时，每一层实际放进去几条：

| 层 | 45 个探针轮次里有内容的次数 | 占比 |
|---|---|---|
| `slots`（槽位表） | 45 | **100%** |
| `recent`（最近原文） | 45 | 100% |
| `summaries`（摘要） | 30 | 67% |
| `recall`（长期召回） | 10 | **22%** |

**「四层架构拿了满分」这句话是错的。** 分数几乎全部来自**槽位层**——
它是唯一一个「只要开了就必然命中」的层。长期召回层在相当多的探针上**一条都没召回**
（检索词和问题没有重叠）。**把「我插了一个结构化的槽位表」讲成「我的四层记忆架构很强」，
被追问一句就散了；自己先把这行数字摆出来，反而是最稳的。**

### 这份评测**测不到**什么

1. **槽位覆盖不到的事实，一条都没测。** 探针查的全是槽位表里的字段。
   用户说过的「我下周三要去仲裁」这种**没有对应槽位**的信息，保持率**不含它**。
2. **`layered` 在换算型上恒为 1.000 是同义反复**——槽位层就是为这些事实设计的，
   它不渲染出来才是 bug。**这个 1.000 不代表任何效果。**
3. **提示词里有 ≠ 模型会用。** 全文最要紧的一条局限。
4. **助手回复是假的**（一句不含数字的套话），所以真实对话里助手引用过的事实，
   占的位置和这里不一样。
5. **摘要是规则拼的，不是模型写的。** 换成模型摘要这一列大概率会变——
   但那就换来了一个不可复现的数。**这是刻意的取舍，不是没做。**

### 记忆层接进主链路时，顺手修掉的三个真 bug

这三件事都是**先写测试、再发现原来的代码是错的**，不是设计时想到的：

**（1）槽位表接进去之前，它在主链路里根本没被调用过。**

`fill_args()`（槽位层的全部意义所在——把从对话里抽出的精确值填进工具参数）
写好了、有测试、**但没有任何地方调用它**。等价于「槽位层只存在于测试里」。

具体会怎样：第 1 轮用户说「月薪 12000」，第 20 轮问「那到底能赔我多少钱」——
隔着 19 轮，早就出了 6 轮窗口。**在这之前，模型既看不到那个数字，也看不到城市**，
只能照着模板问一遍「请提供您的月工资」。

现在补上的是**三根线**，每根对应一种真实的失败：

1. `remember` 节点把记忆块（槽位 / 窗口 / 摘要 / 长期召回）组装出来；
2. 这个块**同时**送给答案提示词**和**工具循环的系统消息——两条路都要，少送一条就有一半场景是聋的；
3. 槽位**回填**模型漏掉的工具参数——漏掉的值用槽位里已核实的事实补上（**只补空的，绝不覆盖**）；
   真的补不出来才变成一句中文追问「还缺月工资，麻烦您补充一下」。

**（2）一个纯粹的哈希 bug，让幂等和防重复两道机制同时失效。**

`args_hash` 直接拿 `json.dumps` 的结果算指纹。问题在于同一个值有**两种写法**：
模型从 Function Calling 里传出来的是 JSON 整数 `12000`，而槽位层存的是浮点 `12000.0`。
两者序列化出来的字符串不同 → 指纹不同 → **同一个请求被当成两个不同的请求**。

两个后果都不会报错，只会静默地少干活：

- 幂等缓存**永远命中不了**跨这两条路径的重复调用；
- 防重复调用那道闸门**可以被模型绕过去**——这次写 `12000`、下次写 `12000.0` 就算新调用了。

修法是加一个规范化函数：整数形式的浮点统一转成整数，对 dict/list 递归处理。
**刻意不转换字符串**——「12000」和 `12000` 是两码事，那是类型错误，该由入参校验去报，不该被悄悄抹平。

**（3）“缺什么参数”这一栏，被两个不同的东西混着算。**

工具报「你少传了 `monthly_wage`」，和槽位表报「我的表里没有月工资」，是**两件事**：
前者是**这次调用缺**，后者是**整体缺**。第一版把它们混在一起，导致一个真的
**类型错误**（枚举值写错）被测成了「缺一个必填字段」。

修法是两道过滤：必须是**字段级**的 `missing` 错误，**并且**和槽位表报的缺失取交集。
这样「枚举写错」不会被误报成「缺字段」，也不会出现「问了一个其实已经有的值」。

> 这三个 bug 都不是「代码写错了」，而是**「代码很对，但没接上/接错了」**——
> 这类问题不跑一遍主链路是看不出来的，测试全绿也没用，因为它们测的是单元，不是接线。

## 产品壳：怎么把它当场演示出来

有三个入口，**但它们不是三套实现**：

```bash
juris ask "被辞退有补偿吗？" --trace   # 终端：问一句就走（日常用这个）
juris chat                            # 终端：多轮对话（记忆层最直观的地方）
juris serve --port 8000               # 浏览器：http://127.0.0.1:8000

python scripts/demo.py --mode replay   # 终端：离线重放，零成本，不联网
```

前三个是同一个东西（`client.py` 的门面，四个子命令都在 `cli.py` 里），
`scripts/demo.py` 是**开发视角**的那个——它会把"系统里发生了什么"逐条摊开打，
适合看链路；`juris ask --trace` 是它的精简版。

⚠️ **这里是两件事，别混说**（第一版这段写成了一句"所有入口都调
`AgentRunner.stream`"，那是错的）：

| | 走哪条 | 事件层（`api/events.py`） |
|---|---|---|
| `juris serve`、`scripts/demo.py` | `AgentRunner.stream` | **经过**——图里的更新被翻译成对外事件，终端打印或发 SSE |
| `juris ask` / `juris chat` | `AgentRunner.ask` | **不经过**——直接拿最后那份 `AgentState` |

两条路跑的是**同一张图**（同一个 `AgentRunner`），所以"路由、闸门、引用校验"
这些行为完全一致；差别只在**出口**：事件层那条能看见中间的每一步，
`ask` 那条只看见结果（想看中间步骤用 `--trace`，它读的是状态里的 `trace`，
和事件层是两份数据源）。

**为什么要共用那一层，而不是各写一份**：演示脚本和网页各自解释一遍图里发生了什么，
就会出现"终端说走了工具循环、网页没显示"这类**两个界面互相矛盾**的问题，
而排查这种矛盾比修它更费时间。共用一个翻译层之后，
"两边事件名一致"是**结构上保证的**，不是靠人去对齐的。

### 一次提问在网页上的样子

事件流按发生的顺序推进，每个事件对应界面上一段：

| 事件 | 什么时候发 | 界面上显示成 |
|---|---|---|
| `memory` | 组装完记忆（槽位/窗口/摘要/长期召回） | 这一轮看到的历史、占了多少 token、还缺什么 |
| `route` | 规则路由判完 | 走哪条路 + **为什么**（"命中『写一首』等非劳动法词汇"） |
| `retrieval` | 检索完 | 命中几条、哪几条（带条文正文，可点开） |
| `tool_call` / `tool_result` | 工具循环每一步 | 调了什么工具、传了什么参数、成功还是重试 |
| `missing` | 工具报缺参数 | 还需要用户补哪几项 |
| `thinking` | 模型在推理（**每 120 字节流一次**） | 一个转圈的提示，**不显示推理内容** |
| `answer` | 逐字增量 | 正文逐字出现 |
| `citations` | 引用校验完 | 引用了 2 条 / 编造了 1 条（已删） |
| `guard` | 触发防死循环闸门 | （红字）哪道闸门、为什么触发 |
| `refusal` | 判越界 | 拒答原因 + **建议去问谁** |
| `error` | 出错了 | 错误信息（不吞） |
| `done` | 收尾 | 权威答案、引用列表、成本、收尾原因、请求 id |

### 第二个视图：工具箱（页面里不过模型的那一半）

网页现在有两个视图，**它们不是同一个东西的两种皮肤**：

| | 问答 | 工具箱 |
|---|---|---|
| 走哪条 | 整张图（检索 + 工具循环 + 生成 + 引用校验） | **只调执行器**（`POST /api/tools/{name}`） |
| 要 key 吗 | 要 | **不要** |
| 快 | 几秒 | 毫秒 |
| 花钱 | 花 | **不花** |
| 同输入两次同结果 | **不一定**（模型有随机性） | **一定** |

**为什么必须把它单拎出来**，而不是把五个计算器塞进聊天框：
用户问「我干了 3 年该拿多少补偿」，聊天给的是**普法**（解释 + 法条）。
但一个要拿这个数去跟公司谈的人真正需要的是**反复试**——把工龄改成 2 年 11 个月
试试、把月薪改高看看会不会触发封顶。在聊天框里做这件事，
每改一个数就要等模型回一遍、花一次钱，而且**两次的措辞可能不一样**——
用户没法确认"是我改的数字起作用了，还是它换了个说法"。

工具箱里跑的是**纯函数**：同一组输入永远同一个答案。这才是"可核验"能落地的地方，
和法条要附原文编号是同一个道理。

#### 表单是**从后端 schema 现场生成**的，前端不认识任何工具名

`GET /api/tools` 返回注册表里每个工具的名字、人话标签、分组和 `args_schema`
（JSON Schema），前端照着长表单。**后端加一个工具，刷新页面就多一张表单，
一行前端代码都不用改。**

反过来（前端手写每张表单）的坏处不是"多写点代码"，而是**新工具上线后界面上
根本没有入口、而且不报错**：没有异常、没有红字，只是少了一个按钮。
这种"少了一个东西"的坏法没有任何机制会提醒你。

界面上唯一能在后端找到出处的是 `ToolSpec` 的两个新字段：

| 字段 | 给谁看的 | 为什么必须有 |
|---|---|---|
| `label` | **人**（「算经济补偿 / 赔偿金」） | 界面直接显示 `calc_severance` 太糙 |
| `group` | **人**（「算钱」/「查合同条款」） | 按"用户什么场景会用"分，不按代码模块分 |

> ⚠️ **这两个字段没有在前端再抄一份表。** 抄一份的后果是那张表会漂移——
> 新工具加进来了，注册表有、前端表没有，界面上就少一张卡片，**且不报错**。
> 显示名和分组属于工具本身，就该和工具注册在一起。

#### 写这个视图时撞出来的两个坑

**（1）pydantic 对枚举字段不写 `enum`，写 `$ref`。**

`calc_severance` 的 `cause` 字段（十种解除情形）在 `model_json_schema()` 里长这样：

```json
{"$ref": "#/$defs/TerminationCause", "description": "解除或终止的情形。必须选一个最贴近的：…"}
```

前端读 `properties.cause.enum` 拿到的是 `undefined`，于是**渲染成一个自由文本输入框**，
用户得手打 `illegal_dismissal` 才能算对。它不报错、不崩，只是**静默地把一个
该做下拉框的字段做成了填空**——而"十种情形选错一种，后面的数全错"。

这是 `test_enum_args_reach_the_ui_as_enum` 抓出来的。修法是在服务端加
`_inline_refs()` 把 `$ref` 就地展开（递归展开 + 防自引用死循环 + `$ref` 同级字段优先），
而不是让前端自己解析——**前端要是有两份实现，第三份就会出现在下一个视图里。**

**（2）降级提醒在去往界面的路上被丢掉了。**

执行器的 `ToolOutcome.warnings`（目前只有"走了降级路径"一种）原本到
`api/events.py` 就断了：`payload` 带得过去，`warnings` 没有对应字段接。
后果是**降级结果被当成正常结果用**——而"降级最怕的就是被当成正常结果"。
现在它一路走到界面（`ToolCallRecord.warnings` → `tool_result` 事件 → 黄色 ⚠ 条）。

这一条是"**加个字段要动三个文件**"的那种改动，很容易图省事不做。
不做的话，界面照样能用、测试照样绿，只有真降级的那一次会悄悄骗人。

### 四个刻意的取舍

**（1）同步的图被丢进线程池跑，不是直接在事件循环里跑。**

不改的话，"流式"会**看着坏掉**：整段答案在最后一次性蹦出来。
因为同步代码在事件循环线程里一跑到底，中间根本没有机会把已经收到的字发出去。
代价是要处理线程边界——**而这一层就藏着一个真 bug，见下面第 3 条**。

**（2）依赖装配放在 `lifespan` 里，不在 import 时。**

写在模块顶层的话，`import juris_agent.api.app` 就会加载 1GB 的嵌入模型：
跑测试从 11 秒变成几分钟，`uvicorn --reload` 每敲一个键重载一次模型。
**这个代价买不到任何东西**——路由是可以独立定义的，装配不是。
所以接口里读 `request.app.state.runtime`，没装配好就返回 503 并说明原因。

**（3）前端是「一个 HTML 文件、零外部请求」，不引框架、不引 CDN。**

三个理由，一个比一个实际：演示现场可能连不上外网（CDN 在国内时通时不通）；
面试官可能一边看你改代码一边刷新页面；以及"能打开一个文件就看到全部"这件事，
比"组件复用"在这种规模的项目上值钱。代价写在文件头注释里：没有组件复用。

**（4）承认"关掉页面不会取消已经发出去的模型调用"。**

用户点了停止或直接关标签页，Python 的线程**没法从外面杀掉**，
所以那一次调用仍然会跑完、仍然会计费。诚实的做法是把这句话写进代码注释和
这一节里，而不是假装我们已经取消了——**假装取消会让成本报表难解释**：
账上多出来的钱会被当成 bug 去查。

### 真机跑出来的四件事

把服务真的起起来、用真 key 真的问，才暴露出来的：

**（1）成本报表里的 `prompt_tokens` 一直是 0，金额永远走"粗估"那条退路。**

`LLMClient` 的账本是**按线程记的**：哪个线程开的账，只有那个线程读得到。
账是在工作线程里开的（图在那儿跑），而算钱的那行代码在**事件循环线程**里——
在那边读只能拿到一本空账。而且它**不报错**：账本对"没开过账的线程"设计成返回全 0。

这个 bug 在真机上跑通的第一版里就在，没人发现，因为**退路算出来的金额看着挺合理**。
是盯着 `basis` 那一行想"为什么会走退路"才挖出来的。
修法是在工作线程里**把账抄下来**再传出去；回归测试用了一个刻意模仿
"线程本地"行为的假件——**假件比真件"好用"的地方，正是 bug 藏身的地方**。

**（2）「帮我写一首关于秋天的诗」没被判成越界。**

路由词表里一个词都不命中 → 兜底走法条路 → 白检索一遍、精排白跑 3.4 秒 →
最后由模型在正文里自己拒绝。**模型拒得挺好，但系统的判定是错的**：
`finish_reason` 记成 `answered`，于是"拒答率"这类指标全统计不到它。

修法是往 `configs/router.yaml` 加词，但踩到了第二个坑：匹配是
**连续子串**不是分词，一开始只收了「写一首诗」，而「写一首**关于秋天的**诗」
中间隔着字、一个都不命中。最后收的是「诗」「写一首」这种**词**，
同时**刻意不收**「写一份」「写一段」——仲裁申请书、情况说明是正当需求，
**宁可漏，不可误伤**。两个方向都有测试盯着。

**（3）`replay` 模式把账单报成了 `¥0.138040`，而那一轮一个接口都没打。**

缓存命中的那一轮，客户端**刻意不记账**（那笔钱当初已经记过了），
于是算钱的代码掉进退路，用状态里记的 token 数（那是**当初真调时**的数）算了一遍钱。
公式正确、数据真实——**只是问的是一年前的问题**。

这类错误最危险的地方是**那个数看着太正常了**。所以修法不是"记得别算错"，
而是给成本对象加一个显式字段 `billable`（这笔钱到底花没花），
前端、终端、以后的报表**一律先看它再看金额**。三处显示各写一遍判断必然会分叉，
所以措辞统一在 `observability/cost.py::describe_cost` 里，一处改、处处改。

**（4）界面上印着「请求 xxx」，可服务端日志里**一条都搜不到**。**

界面上每个回答底下都有一串请求 id，设计意图是"出问题时把这串字发过来，
一 grep 就能捞出这一轮的全部日志"。真去 grep 才发现是 **0 条**。

原因有两层，叠在一起：

- 第一层：**成功的一轮根本不打日志。** 日志原来只在出错、会话写回冲突、
  客户端断开时才有。也就是说**这个排查机制在最需要它的场合
  （"这轮回答有点怪，但也说不出哪不对"）里是哑的**——没报错，所以没日志。
- 第二层：`_run_turn` 自己生成一个 id 塞进 `done` 事件，调用方又
  **自己生成另一个** id 去绑日志上下文。两个串格式一样、都正常生成，
  **但不是一个东西**。用户抄下来的那串，在日志里连格式匹配都做不了。

修法：id 只在调用方生成一次、往下传；每轮结束补一条 `一轮结束` 日志，
带上路由、收尾原因、token、会话 id。还有个收尾细节——
建会话那一步（"新建会话"）原本在 id 生效范围之外，等于**同一个请求的日志
被劈成两半**：一半按 id 能搜到，另一半只能靠时间戳猜。
把 `bind` 拆成**先绑 id、建完会话再补会话 id**两层套，才算真的"串起来"。

这条也有测试，而且**测试本身返工过两次**——第一版测的是一条根本不存在的日志
（详见 `tests/test_api.py` 里那个类的注释）。

> 共同点：四件事都**不是逻辑写错了**，而是**接线接错了 / 判断顺序错了 /
> 机制搭好了但没真在工作**。四条都有回归测试，而且都**验证过
> "把修法撤掉测试会红"**——测不出 bug 的测试是装饰。

### 实测成本（真实运行，全文见 [`reports/cost.md`](reports/cost.md)）

八条混合题、**真调 API** 的实测（生产 `inject_k = 8`，模型 `deepseek-flash`）：

| | 值 |
|---|---:|
| 单题成本 P50 / P95 | **¥0.021 / ¥0.040** |
| 最贵 / 最便宜 | 差 **69.7 倍**（计算题要走工具循环，闲聊一次调用就完） |
| 钱花在哪 | `生成答案` **65.5%**、`工具循环` **34.1%**、闲聊 0.4% |
| 越界拒答（"帮我写首诗"） | **0 次模型调用、¥0**——规则层就挡掉了 |
| prompt 缓存 | 命中率 **71.4%**，输入开销省 **64.3%** |

三条**必须一起看**的注意事项（否则这几个数会被用错）：

- **别拿「平均价」拍预算。** 题与题之间差近 70 倍，预算要按最贵那一档拍。
  另外，拒答题是 ¥0——它**不是一个「便宜价」，是「这笔交易没发生」**，
  所以它不参与"最贵/最便宜"这个倍数（拿它做分母会得到一个假的"无穷倍"）。
- **别把缓存那条读成「用户越多越省」。** 真正命中的是
  **「同一段前缀被反复发」**（同一题的工具循环里，后一次调用把前一次的整段对话
  重发了一遍）；用户之间并不共享多少前缀。这个区别决定它**能不能扩**：
  一轮的第一次调用永远是冷的，而且命中率**会随工具循环轮数变高**——
  也就是说它会被"模型爱多绕两圈"顶上去，**不能当优化得好的证据**。
- **「少注入几条法条」省不了多少钱。** `inject_k` 8→2：生成阶段输入 token 降 19.9%，
  但**每题成本只降 9.7%，而召回掉 10.0 个百分点** → 不划算。
  原因是占成本 34.1% 的工具循环**完全不随 `inject_k` 变**
  （那一档塞的是工具定义和前几轮对话，不是检索结果）。
  真正有空间的省钱方向在别处：少绕一轮工具循环、把工具定义压短。

金额全部按 `configs/pricing.yaml` 的牌价表算（`as_of` 原样打出来），
**是估算不是账单**。重放同一批问题**成本是 0**，可以离线反复演示。

## 改坏了怎么拦住：CI + Recall 回归门禁

「你怎么防止改坏」这个问题有两半答案，**缺一半都不成立**：

| | 管什么 | 坏了的时候 | 谁在做 |
|---|---|---|---|
| **单测** | 系统还**跑不跑得通** | 立刻红 | 764 条测试 |
| **门禁** | **质量有没有掉** | **不会红** | `scripts/check_recall.py` |

第二行是这个项目里最容易被跳过、也最值得讲的一格。Recall 从 0.90 掉到 0.85，
**所有测试照样全绿、代码照样跑得好好的**——只有拿数字跟上一版比才知道掉了。
所以门禁不是"再多写点测试"，它是另一件事：**得连着一次真实的测量**。

### 门禁最容易死在"误报"上，不是漏报

一条红了但其实没事的门禁，发生两三次之后，所有人就学会忽略红色了，然后它死了。
所以 `scripts/check_recall.py` 的判定顺序是刻意的，**三步不能换**：

1. **有基线吗？** 没有 → 状态 `NEW`。**不能判 PASS**——那等于"没有门禁"。
2. **语料或评测集变了吗？** 变了 → 状态 `STALE`，**拒绝比较**。
3. 才轮到比数值。

第 2 步是关键，也是这个脚本里最值钱的二十行。基线数字只在
「**某一份语料 + 某一份评测集**」上成立。语料一变，数字涨跌**都是合法的**，
这时候照常做一个差值比较，两种结果都比不比较更坏：

- 数字**涨了** → 测试绿，你以为没事，其实是语料换了；
- 数字**跌了** → 测试红，你去查一个**根本不存在的 bug**，查一下午。

所以基线里一并存 `corpus_hash` / `gold_hash`，对不上就退出码 3，
提示"先确认这版改动确实动了语料，再 `--update-baseline` 重新标定"。
**把"该不该重新标定"这个判断明确交回给人**，而不是让脚本替你猜。

### 门禁卡的是哪个指标

卡 `recall_art@5`（按条算覆盖率），**不是** `recall_hit@5`（蒙中一条就满分）。
这是本项目消融的结论之一，门禁跟着它走：多条款组合题召回 1/3，
hit 口径给满分 1.0，art 口径给 0.33。**而漏掉的那两条才是答错的原因**——
hit 口径对这件事完全看不见。三个刻度同时用：

- **绝对下限**：低于这个数一定是坏事；
- **相对基线 + 容差**：比上一版掉了多少；
- 两者**都要满足**才算过。只有相对值时，"一直很低但一直没变"会永远绿；
  只有绝对下限时，一次小退步只要没过线就没人管。

### 三条门禁，CI 里只有一条会真跑

| 门禁 | 守什么 | 要 ml extra？ | CI 里 |
|---|---|---|---|
| `bm25-test` | 数据层：清洗 → 条级切分 → 词典 → BM25 | 不用 | **跑** |
| `dense-test` | 稠密单路（换编码器最先在这里显形） | 要 | SKIP |
| `prod-arm-test` | **生产臂**（与线上 `runtime` 同一套装配） | 要 | SKIP |

不装 ml extra 是因为：一次 CI 要下载 2.5GB 的 CUDA torch 加一个 bge 模型，
跑十几分钟——**而"慢到没人愿意等"的 CI 会被关掉**，那才是真的什么都没守住。
想跑全的用 `workflow_dispatch` 手动触发（`recall-gate-full` job）。

要紧的是**别把 SKIP 说成 PASS**：脚本会在汇总里单独打一行
`⚠️ 跳过的（没跑 ≠ 通过）`，CI 日志里看得见自己少跑了什么。

> 三条门禁的"守什么"写进了 YAML 的 `guards` 字段，而且**有测试要求它非空**。
> 理由很实际：门禁红了的时候，看的人（包括三个月后的自己）得知道该去翻哪一块代码。
> **没有这句话，红色只是一个数字。**

> 全跑一次要等好几分钟，人就会开始"懒得跑"，然后消融表悄悄和代码对不上。
>
> **跑评测前把 `JURIS_AGENT_LLM_MODE` 设成 `record`。** `off`（默认）**既不读缓存也不写缓存**，
> 结果既费钱又不可复现。`replay` 是给 CI 的：零成本、离线、逐字节可复现。
>
> ⚠️ **但别用 `record`/`replay` 去测走 LLM 的臂的延迟**——缓存命中会让 6.7 秒塌成 40 毫秒，
> 而指标不变。要那个数字，得单独切 `off` 跑一次。生成器会读 `JURIS_AGENT_LLM_MODE`，
> 对走 LLM 的臂在表里打 ⚠️ 标记；**带 ⚠️ 的耗时不要引用。**
>

> `fixtures/replay/llm/`（该目录共 556 个录制文件，评测集和消融实验用的也在里面），
> 所以不需要 key、不联网、成本 0。
> 想换成自己的问题，得先 `--mode record` 跑一遍把调用录下来；
> 没录到的问题在 replay 下会**响亮地报错**（`ReplayMiss`），
> **不会退化成"随便调一次真模型"**——那样就分不出"离线可复现"和"我又联网了"。
>
> ⚠️ **`uvicorn` 起服务时会加载嵌入模型和精排模型**（约 1GB 内存、20-30 秒），
> 所以 `/api/health` 在那之前返回 `ready: false`。这是**刻意**的：
> 装配放在 `lifespan` 里，不在 import 时——否则跑一次测试就要多花几分钟。
> 忘了带 `--extra ml` 时也一样：服务能起来，`/api/health` 会说明缺什么。

## 诚实性边界

- 本项目的工具输出**不构成法律意见**。合同体检只做可程序化的形式合法性判定
  （条款是否存在、数值是否超限），实质公平性需执业律师判断。这一点写进了
  `review_contract` 的返回体内。
- 语料版本与生效日期需人工核对。法律有修订，用旧版本条文回答是真实的法律风险。
- 所有指标都会附 `n / eval_set_hash / corpus_hash / prompt_version / config`，
  测不出来的数字不会写进 README 或简历。
