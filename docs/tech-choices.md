# 工具选型：每个依赖为什么是它

这份文档回答一个问题：**"你项目里为什么用 X？"**

写法是刻意的——**先写"不用它会怎样"，再写"用了它换来什么"，最后写"它的代价是什么"**。
只写"因为 X 好用"的选型理由是废话，面试官一追问就露馅。凡是能给数字的都给了数字，
凡是没有实测支撑的都会明说"这条是拍脑袋，没测"。

---

## 0. 一句话总览

| 层 | 选了什么 | 一句话理由 |
|---|---|---|
| 语言/包管理 | Python 3.12 + uv | uv 装得快、锁得死；锁在 3.12 是因为 torch 的 CUDA wheel 还没出 cp314 |
| 数据校验 | Pydantic v2 + pydantic-settings | 配置和数据结构在一个地方定义，写错立刻报错，不用等运行时 |
| HTTP | httpx | 同步接口够用，且能挂 `MockTransport` 做故障注入测试 |
| 日志 | structlog | 结构化字段能被程序消费，纯文本日志只能靠人眼 |
| 中文分词 | jieba | 中文没有空格，不切词 BM25 直接退化成"整句精确匹配" |
| 稀疏检索 | rank-bm25 | 纯 Python、一百行，**好读好改**——这是为了消融里的"切分臂"能自由换 |
| 稠密检索 | sentence-transformers + BAAI/bge-base-zh-v1.5 | 中文短查询检索中文长文档的公开基线，768 维刚好 |
| 向量索引 | **numpy 暴力检索**（默认）/ faiss-cpu（对照臂） | 5.3MB 的索引做近似检索是负优化，见 §4 |
| 精排 | BAAI/bge-reranker-base（cross-encoder） | 融合丢掉的分数信息，靠它补回来 |
| 生成模型 | DeepSeek（flash 生成 / pro 判题） | 便宜、中文好、OpenAI 兼容；判题用更强的那个，见 §7 |
| 评测切分 | 自写，不用 RAGAS / DeepEval | 见 §8——这是**主动不用**，理由比用了更重要 |

## 1. Python 3.12 而不是 3.14

**不用它会怎样：** 直接 `uv sync --extra ml`，报错：

```
error: Distribution torch==2.6.0+cu124 ... doesn't have a source distribution
       or wheel for the current platform
hint:  You're using CPython 3.14 (cp314), but torch has wheels with ABI tags
       cp312, cp313, cp313t
```

**代价：** 锁在 3.12，用不到 3.13/3.14 的新语法（自由线程、JIT 预览）。

**为什么还是这么选：** 这个错发生在**依赖解析之后、装包之前**，报错文本里
"doesn't have a source distribution" 会被第一反应当成网络问题或镜像问题，
实际跟网络无关。钉死版本把这个坑变成不可能发生，代价是零——
本项目的代码没有一个特性需要 3.13+。

同时写了 `.python-version`（内容 `3.12`）。**只改 `pyproject.toml` 不够**：
uv 在 `requires-python` 允许的范围内仍会优先挑机器上最新的解释器，
`.python-version` 才是那个"别自作主张"的开关。

## 2. uv 而不是 pip / poetry / conda

**不用它会怎样：** pip 装 torch 那套（2.5GB）要几分钟，装到一半断了得从头来。

**换来什么：** 解析+下载并行、有硬锁文件（`uv.lock`，进 git），
`uv run` 自动保证跑在正确的虚拟环境里——**减少了一整类"我这跑得通啊"的扯皮**。

**代价：** 生态比 pip 新，少数包的特殊安装方式（比如本地路径依赖）uv 支持得晚一点。
本项目没碰到。

**为什么不用 conda：** 它的强项是跨语言二进制（R、CUDA 工具链）。本项目所有依赖
都是纯 Python 或 PyPI 上的 wheel（torch 的 CUDA 版走 PyTorch 官方 index 也能装到），
用不到 conda 的能力，却要吃它"环境难复现、锁文件不完整"的亏。

## 3. Pydantic v2 + pydantic-settings

**不用它会怎样：** 配置从环境变量读进来是一堆 `os.environ.get(...)`，
拼错了返回 `None`，然后在三个模块之后爆一个 `AttributeError: 'NoneType'`。

**换来什么：** `Settings` 一个类，字段类型、默认值、环境变量别名都在一处声明；
`ArmConfig`（消融的每一行）也是一个 Pydantic 模型，所以"一条臂"能被序列化成 JSON
写进 `reports/ablation.json`——**表里每一行都能倒推出跑它的那个配置对象**。

**代价：** v1→v2 是不兼容大改，网上大量 v1 的答案直接抄会报错
（本项目踩过一个：`self.model_fields` 在 v2 里要写 `type(self).model_fields`）。

**踩过的坑，留档：** `env_prefix="JURIS_AGENT_"` 会让字段 `deepseek_api_key`
去找 `JURIS_AGENT_DEEPSEEK_API_KEY`，而 `.env` 里写的是通用名 `DEEPSEEK_API_KEY`。
症状特别误导——`.env` 加载成功了、`os.environ` 里确实有 key，只有 `Settings` 读到 `None`，
表现为"我明明配了 key，LLMClient 却说没有"。
修法是 `validation_alias=AliasChoices("DEEPSEEK_API_KEY", "JURIS_AGENT_DEEPSEEK_API_KEY")`，
**两个名字都收**：前者是业界通用名（复用人已有的 key 不用改名），后者是自己项目的命名空间。

## 4. 稠密检索：为什么**不**用向量库（Chroma / Milvus / Qdrant）

这是最值得讲的一条，因为**原计划里写的就是 ChromaDB，是实测之后拿掉的**。

**规模事实：** 语料 1730 条、768 维 float32 → 向量总大小 `1730 × 768 × 4B ≈ 5.3 MB`。

**在这个规模上，向量库唯一的卖点是近似加速，而近似只会让 Recall 变差。**

- 暴力点积（`numpy` 的 `mat @ q`）是**微秒级**的；
- 它是**精确**检索——`F/dense 精确` 这条臂的 Recall 是数学上界；
- 向量库的查询开销（网络/进程往返、元数据过滤、结果组装）**比暴力算还大**。

**代价换来什么：**

| | 用 Chroma | 用 numpy |
|---|---|---|
| 装完的依赖 | +300MB（kubernetes / onnxruntime / grpcio / opentelemetry） | 0 |
| 冷启动 | 拉起持久化客户端 | 读一个 `.npz` |
| Recall | 相同或更差（HNSW 是近似的） | 精确 |
| 测试速度 | 要起服务或开临时目录 | 纯内存 |

**保留 faiss-cpu 干什么：** 它不是拿来当默认后端的，是拿来当**对照臂**的。
`F/dense 精确` vs `F/dense IVF(nprobe=1)` 这条轴回答的是
"为了省时间，近似检索让我掉了多少 Recall"——这是个**有数字的**工程判断。
而"Chroma vs FAISS"作为对照轴是没意义的：两者都是精确检索时 Recall 必然相同，
差别只在 QPS，那属于压测不属于召回消融。

**什么时候该反过来用向量库：** 语料上到十万条量级，或者向量维度上到 4096。
这句话得能说出来，否则就变成"我不用向量库"是背下来的结论。

## 5. 分词与稀疏检索：jieba + rank-bm25

**jieba 不用会怎样：** 中文没有词边界。不切词，BM25 的"词"就变成整句话，
查询和文档必须几乎逐字相同才匹配得上——稀疏这一路直接废掉。

**为什么不用更"先进"的分词：** 预训练分词器（比如 BERT 的 wordpiece）会产生
大量词表外的碎片，对 BM25 这种**精确词匹配**模型是负作用。jieba 的
`add_word` 还能塞法律领域词典（"事实劳动关系"、"竞业限制" 这种不能被切错的词）——
这是 `configs/legal_dict.txt` 的用途，它同时是 A 组 `dict=on/off` 这条消融轴。

**踩过的坑：** 词典里塞了短词（"工资"、"加班"），结果 jieba 把
"加班工资" 切成了一个词，反而破坏了更细的匹配。现在词典**只留长词**，
这个发现写在 `configs/legal_dict.txt` 里。

**为什么用 rank-bm25 而不是 Elasticsearch / Whoosh：**
ES 要起服务、要 JVM，而本项目**需要频繁换切分方式**（A 组有 4 个切分臂 × 词典开关）。
`rank-bm25` 是纯 Python 一百行左右，**索引是一个内存对象，重建是毫秒级**——
它换来的不是性能，是"改一行切分代码马上能看到指标变化"的实验速度。
1730 条的规模下，ES 的检索优势完全体现不出来，运维成本倒是实打实。

## 6. 稠密模型：BAAI/bge-base-zh-v1.5

**选它的理由：** 中文、短查询检索长文档、公开可下载、768 维、base 尺寸（约 400MB）。
这是中文检索里最常见的公开基线，选它意味着**指标可比**——
别人复现我的数字不需要先相信一个我私有的模型。

**为什么是 base 不是 large：** large 是 1024 维、参数 3 倍。
本项目要做**完整消融矩阵**（几十条臂 × 269 道题），base 跑得完，large 会把
实验周期拉长到"懒得跑"的程度——**而"懒得跑"才是消融表过期和代码对不上的真实原因**。

**踩过的坑（重要）：** `bge-*-zh-v1.5` 系列在**短查询检索长文档**时，
要求给**查询**加一句指令前缀：

```
为这个句子生成表示以用于检索相关文章：
```

**文档侧不加。** 这个前缀漏掉不报错、不警告，只是指标白掉几个点——
是最典型的"静默降级"。所以它被写成模块级常量 `BGE_QUERY_INSTRUCTION`
放在 `retrieval/dense.py` 顶部，并且在 `Encoder` 里用参数区分
"这是查询还是文档"，而不是靠调用方记得加。

## 7. 精排：BAAI/bge-reranker-base

**不用它会怎样：** RRF 只看名次、不看分数——"以 0.99 相似度遥遥领先"和
"以 0.51 险胜"在 RRF 眼里一样。这个信息损失必须有人补。

**换成什么：** cross-encoder 把 `(query, 文档)` 拼起来过一次模型，
比 bi-encoder 的"先各自编码再算余弦"准得多——因为它能看到两者的交互。

**代价（这是这条选择的重点）：** cross-encoder 要把
**1 次查询 × 20 个候选 = 20 次前向**，是本项目里最慢的一段
（消融表的 `p95` 列会直接暴露出来）。

**所以有了超时降级：** `Reranker` 用单线程池 + `future.result(timeout=...)`，
超时就用融合的原始排序返回，并在 `PipelineResult.warnings` 里明说"降级了"。

**一句必须说清的话，写在代码注释里了：** Python 的线程**杀不掉**，
超时后那次前向仍在后台跑完。**省下的是用户等待时间，不是算力。**
把这句话说清楚，比把超时包装成"优化"要诚实——

## 8. 生成模型：DeepSeek，且**生成与判题用两个不同的模型**

**选 DeepSeek 的理由：** 便宜、中文强、OpenAI 兼容协议
（意味着换供应商只需改 `base_url`，不需要改代码结构）。

**为什么分两个：**

- `model_gen = deepseek-flash`——日常生成，便宜；
- `model_judge = deepseek-v4-pro`——**判题和造评测集**，用更强的那个。

理由是**判题模型的能力上限就是评测结果的可信度上限**。用弱模型判强模型的答案，
指标里混进了"判题者看不懂"的噪声。这条在评测项目里比在应用项目里重要得多。

**实测踩的坑（这个坑很深，值得记）：** DeepSeek 这两个都是**推理模型**，
思维链也计入 `max_tokens`。设 `max_tokens=32` 时，模型把 32 个 token 全花在
思考上，`content` 返回**空字符串**，而 `completion_tokens=32`、
HTTP 状态码 **200**——所有字段都正常，只有一个空正文。

**这是最危险的一类失败：静默的、看起来成功的失败。**
修法：

1. `_post()` 在 `status==200 且正文为空 且 completion>0` 时抛 `LLMTruncated`
   ——把它变成一个**会响的错**；
2. `chat()` 捕获它并自动把 `max_tokens` **翻 4 倍重试一次**（上限 32768），
   而不是把空串交给调用方、让调用方自己猜该设多大。

缓存键仍用**原始** payload 算——升级是确定性的（同样的输入必然触发同样的升级），
所以 replay 时读到的就是当初升级后的那份响应，**复现性不受影响**。

**另一个刻意的设计：评测路径上 `temperature` 强制为 0。**
不是 0 的话，同一道题跑两次出两个数，消融矩阵**不可比**，
而"不可比"这件事从表面上完全看不出来。

**`.env` 里 `JURIS_AGENT_LLM_MODE` 三挡的含义（容易搞混）：**

| 值 | 读缓存 | 写缓存 | 用途 |
|---|---|---|---|
| `off` | ✗ | ✗ | 交互式开发，每次真调 |
| `record` | ✓ | ✓ | **跑评测**——生成可复现的 fixture |
| `replay` | ✓ | ✗ | CI——离线、零成本、结果逐字节可复现 |

**注意 `off` 既不读也不写。** 评测路径上开着 `off` 会既费钱又留下
不可复现的数字——这是本项目跑消融时**必须**切成 `record` 的原因。
缓存是内容寻址的（对 `{model, messages, temperature, max_tokens, top_p, response_format}`
做 sha256），所以 key 变化会自动 miss，不存在"改了 prompt 却读到旧结果"。

## 9. HTTP 与日志：httpx + structlog

**httpx 而不是 requests：** 目标是同步接口够用，但 httpx 能挂
`MockTransport`——**故障注入实验（F22）靠它**：不碰网络就能造出
超时、500、429、慢响应，然后验证执行层的熔断/退避/降级真的触发了。
用 requests 就得打桩库或者真起一个坏服务。

**structlog 而不是 logging：** 检索的每一段都产出
`(stage, elapsed_ms, n_in, n_out)` 这类结构化字段。**结构化之后这些字段能被程序消费**
（写进 `reports/*.json`、画曲线），纯文本日志只能靠人眼。

## 9.1 Web 层：FastAPI + 裸 `StreamingResponse`，**不用 `sse-starlette`**

**FastAPI 而不是 Flask：** 它是 async 的，而这一层最要紧的事就是"一边收模型吐的字、
一边往浏览器送"。Flask 的同步模型下，要么整段答案在最后一次性蹦出来
（"流式"看着像坏了），要么得自己引一个异步 worker 方案。
另外 pydantic 的请求/响应模型和项目里其他部分是同一套，不用学第二套校验方式。

**⚠️ 这里要写的是"删掉的东西"：一开始声明了 `sse-starlette`，装完没 import 过。**

当时的想法是"SSE 就该用专门的库"，实际写的时候发现直接
`StreamingResponse` + 手写 `event: 名字\ndata: {...}\n\n` 就够了，而且**更好**：

| | 手写 `StreamingResponse` | `sse-starlette` |
|---|---|---|
| 事件形状 | 我们自己定（`api/events.py` 一处定义，终端和网页共用） | 要按它的 API 组装 |
| 断连检测 | `request.is_disconnected()`，一条 if | 它代劳，但我们**本来就要在同一个分支里置取消标记** |
| 心跳 / ping | 不需要（一次问答最多几十秒，中途不断） | 自带，但用不上 |
| 依赖 | 0（FastAPI 自带） | 一个额外包 + 它的版本约束 |

真正让我下决心删的是这个：**一个声明了却没人 import 的依赖，是一个"你以为在用、
其实没在用"的隐患**。面试时被问"为什么选 sse-starlette"，唯一诚实的答案
是"我不记得了"——而**一个答不上来的依赖，比少一个依赖难看**。

代价也如实记：手写意味着断连、心跳这些边界得自己负责。
现在的实现只在**每条事件推送之后**检查一次断连，所以：
① 如果模型正在生成、迟迟没有新事件，断连要等下一个事件才被发现；
② **已经发出去的模型调用不会被取消**（Python 线程没法从外面杀掉），
这一次调用仍然跑完、仍然计费。这两条都写在 `api/app.py` 的模块注释里，
**不假装我们已经取消了**。

## 10. 评测：为什么**自己写**，不用 RAGAS / DeepEval

这一条是"主动不用"，理由比"用了"更值得讲。

**不用它会怎样：** 得自己实现 Recall@k、MRR@10、nDCG@5，大约 100 行。

**换来什么：**

1. **双口径 Recall。** 本项目的核心指标设计是
   `recall_hit@k`（top-k 里**有任意一条** gold 即命中）与
   `recall_art@k`（**覆盖了 gold 的比例**）**必须一起看**。
   多条款组合题上，只报前者会虚高数倍——而现成框架给的是单一 Recall@k，
   正好是那个会虚高的口径。**这不是"造轮子"，是指标口径要自己定义。**
2. **零 LLM 依赖的指标。** 法条有编号，gold 是条文号，
   所有指标**可程序化精确计算**，不需要 LLM 打分。
   RAGAS 那一类框架的核心卖点是"用 LLM 判忠实度/相关性"——
   那引入了一个**会漂移的、要花钱的、不可复现的**评测器，
   而本项目要的恰好是相反的东西。

**代价：** 没有现成的"忠实度/答案相关性"指标。
这两个本项目**放在 Agent 层用另一个方式做**（引用准确率 = 生成的引用编号
是否真的在检索结果里），比 LLM 打分更硬。

**一句话结论：** 用 RAGAS 是在**评测一个法律的检索问题上引入一个不精确的裁判**，
而法律是所有领域里最不该接受不精确裁判的那个。

## 11. 测试：pytest，以及**刻意没用**的东西

**没有用 mock/patch 覆盖核心逻辑。** 工具层、执行层、检索融合这些
是**纯函数或确定性对象**，直接喂输入断言输出即可——
`tests/` 里 360 个测试大部分是这样，跑完是秒级。

**只在真正有外部依赖的地方打桩：** LLM 客户端用 `MockTransport`、
稠密检索用假的 retriever 表。

**一个教训（写进测试注释了）：** 有一次我写了个测试断言
"权重改动会改变排序"，构造里让同一个 id 出现在两路检索结果中——
结果那个 id 因为"两路都投了票"天然占高位，断言失败。
**失败的是测试，不是代码。** 修法是把两路的 id 改成完全不重叠，
让权重的效果无歧义地暴露出来。这类"测试写错了却看起来像代码有问题"的情况，
是消融实验里最浪费时间的一类。

## 11.1 回归门禁：**自己写**，不用 `pytest-benchmark` / `pytest-regressions`

候选方案是 `pytest-regressions`（把输出存成快照、下次比对）和
`pytest-benchmark`（跑多次、比对耗时分布）。两个都没用，理由不同：

**`pytest-regressions` 的模型不对。** 它是"拿这次的输出跟上次存的**逐字节比**"，
适合"这段文本/这棵树不该变"这类断言。而这里要守的东西是
**一个浮点指标不该掉太多**，涉及三件它没有的事：

1. **容差**。检索指标本身有噪声（浮点累加顺序、jieba 词典热加载、
   reranker 分数微差）。逐字节比的话这条门禁每天都会红，
   然后就没人看了。**一条经常红但都不是真事的门禁，比没有门禁更坏。**
2. **数据指纹**。它的快照不知道"当时是拿哪份语料测的"。语料一换，
   快照当然对不上——而这时正确的动作是**重新标定**，不是去查回归。
   自己写才能把 `corpus_hash` / `gold_hash` 一起存进去，并在对不上时
   用**不同的退出码**（3）把"该重新标定"和"真的退化了"分开。
3. **双向阈值**。要同时卡绝对下限和相对基线，快照模型里没有"下限"这个概念。

**`pytest-benchmark` 管的是耗时，不是质量。** 它是好工具，但这里要卡的是
Recall——一个耗时完全正常、测试全绿、代码跑得好好的系统，召回照样可能掉 5 个点。
**这一条是回归门禁存在的全部理由**：单测测"跑不跑得通"，门禁测"跑得对不对"。

**代价老实说：** 自己写意味着这套东西没有社区维护，`judge()` 的判定逻辑
得自己写测试盯着（`tests/test_recall_gate.py` 15 条，测的全是
"门禁会不会骗人"——判定顺序、容差边界、配置写错要报成配置错）。
换来的是一件事：**退出码 1 和 3 的区别是有意义的**，
而 CI 里这两种红该点谁是完全不同的两个人。

## 12. 没有实测支撑的部分（诚实清单）

以下几条是**判断，不是测量结果**，写在这里以免被当成实测结论引用：

- `rerank_timeout_ms = 800`——这个默认值是照着"p95 别超一秒"拍的，
  没有扫过参数曲线。要改成实测的，得跑一轮超时×精排收益的扫描。
- `top_k = 20` / `fused_k = 20`——同上，是常见默认值，没扫过。
  语料只有 1730 条时，`top_k` 再大也只是把整部民法典塞进候选池。
- A 组切分臂里 `fixed_512` 的 512 字符——是按"约 2 个法条长度"拍的，
  没扫过 256/384/768。

**要不要现在补测：** 这几条都属于"补了能给数字、但改不动结论"的量级
（候选数在 1730 条的语料上不是瓶颈）。**写在这里而不是悄悄用默认值，
是因为面试里被问"这个 800 怎么定的"时，"我拍的，理由是这样" 和
"我实测的" 必须能分清楚。**
